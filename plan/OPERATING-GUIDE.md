## 3. Jira rules (D-028)

Every task Anna creates for a sprint must have:
1. **The sprint Process as Parent.** YV20 is a business space and has no Jira sprints, so a sprint is a work item of type **Process** named `Sprint N (DD/MM-DD/MM)` (current: YV20-108 `Sprint 1 (13/10-22/10)`). Every sprint task is created with that Process as its **Parent**. The weekly check reads and updates **only** the tasks whose Parent is the current sprint Process and that were created from 12.10.2026. It never reads or changes the older open YV20 tasks from August and September, or the older Process items (YV20-56, 69, 70, 88). If there is no current sprint Process, it makes no Jira writes at all. Do not rename a sprint Process after its tasks exist, and keep the `(DD/MM-DD/MM)` part: the check finds the sprint by it.
2. **Original estimate** = the hours from the sprint tab. Without it, hours left, "X% done" and the at-risk rule cannot be computed.
3. **Assignee** = the person's Jira display name from `plan/TEAM.md` (for example "Neev Doron", "Or Rosner").
4. **Summary** that says what kind of task it is: `מחקר השדות` or `research` for research tasks; the entity name and `בניית השדות ופריסות עמוד` for build-and-layouts tasks, for example `מוצר: בניית השדות ופריסות עמוד`.

**Carry-over.** A task not finished when the sprint ends is moved to the next sprint Process: open it and change **Parent**, or select several in the List and use Bulk change. The key, comments, time and history stay. The space also has a dropdown field `Sprint`; it is not used and the weekly check does not read it, so do not fill it as a second source.

**Why a Process and not a Jira sprint (13.10.2026).** YV20 is a Jira business space. Its Space settings has no Features or Sprints option, and Backlog and Active sprints do not exist for it (converting the space was not tried). We keep the space as it is. There is no burndown or Complete sprint; the weekly report replaces them. If Jira sprints are wanted later, a Scrum space would be a new project with new keys, and D-028 would change.

## 5. The weekly check

**When and where.** Every Thursday at 07:30 on Lior's Mac (launchd job in `~/yv-weekly`). If the Mac is asleep, it runs when it wakes; if it is shut down, that week is skipped. Each run first updates its copy of the repo, so changes merged to `main` reach it without reinstalling.

**What it measures** (full steps: `.claude/commands/weekly-progress.md`):
- Plan: the sprint's planned tasks from `plan/sprints/<start date>.md`. With no current sprint Process they are measured directly; with one, planned tasks missing from Jira and Jira tasks missing from the plan are listed as mismatches.
- Jira: the tasks under the current sprint Process only (status, estimate, assignee).
- Sandbox: a fresh read-only metadata list of `yv-partial` (29 types, `scripts/weekly/pull-inventory.sh`), compared with the previous one. Since 19.10.2026 it includes where portal work lives: profiles, custom labels and translations, static resources, the site navigation menu, the Experience site bundles, Aura and Visualforce pages, sharing sets and permission set groups.
- Portal and other tasks (no object file): every matching component counts, whatever its date (the portal skeleton was built 07-08.10, before the sprint, and the first check scored it 0). LWCs, site bundles, navigation, labels and translations are retrieved read-only and read against the task: does what the task asks, 100; a screen on mock data (`TODO-APEX`, no Apex), 50, "UI built, data not connected"; partial, 50; nothing, 0. Until Issue #15 defines done per portal task, this is the definition.
- Research: the object file in `tickets/Data Migration/`, on `main`, in an open PR or on any pushed branch. A draft is scored by the legacy fields it has gone through (mapped or dropped) out of the legacy entity's fields, up to 60; `In review` 70, `Approved` 100 (D-030, 19.10.2026). The report says, per research task, how many fields are done, the last push and what is left. Open Stage A PRs are named, with their reviewers. Work that is only on a laptop is not seen: implementers push at the end of every work session.
- Build: the custom fields of the approved object file (except `Not built` rows) found in the sandbox, averaged with the record page.
- Layouts: the record page of the target object, whatever its date (changed 19.10.2026; before, only pages changed since the last run counted, and pages built in July to October scored 0). `scripts/weekly/record-pages.py` retrieves pages and layouts read-only. A record page assigned in the Orders app: 100; a record page built by an orders implementer but not yet assigned in the Orders app, or only a page layout a person edited: 50 (Lior, 19.10.2026); nothing, or only the default layout: 0. A page that is not assigned, or not named `Order-<Object Name>- Record Page`, is also listed as a mismatch to fix. Approved fields not placed on the page are named.
- Git: commits on `main`, PRs and Issues per person, last 7 days.
- Open `question` Issues: who raised them, who owes the answer.

**What it writes in Jira** (tasks under the current sprint Process only; never the Process item itself):
- One comment per task per run: percent done, hours left, the evidence, any mismatch.
- A forward-only status move when the evidence is clear: To Do or Open to In Progress once work appears; at 100%, research to Done and everything else to Ready for testing sandbox. Never backwards; when Jira is ahead of the evidence it only comments.

**The report.** A GitHub Issue titled `Weekly progress <date>: X% done, Y hours left`, emailed to everyone watching the repo. Sections: summary line; one section per person in `TEAM.md` order, ending **on track**, **at risk** (hours left > working days left x 6) or **blocked**; tasks due this week; mismatches between Jira and the evidence; unplanned work; open questions; what the check could not see; Jira changes made; and a **sprint tab update** table, one row per task, for updating the plan workbook.

**Run it by hand:**
- Test, posts nothing and writes nothing to Jira, report in `sources/local/weekly-test-<date>.md`: `bash scripts/weekly/test-weekly-progress.sh` (from the repo folder). Its last lines list any tool call that was refused; there should be none.
- Real run, posts an Issue and writes to Jira: `bash ~/yv-weekly/run.sh`; log in `~/yv-weekly/run.log`.
- Reinstall (safe to repeat): `bash scripts/weekly/install-weekly-progress.sh`.

**If something goes wrong:**

| Symptom in the report or log | Cause | Fix |
|---|---|---|
| "no Jira access" | The Terminal sign-in to Atlassian expired. The desktop app's sign-in does not count for the scheduled job | In Terminal: `claude`, then `/mcp`, sign in to Atlassian (and Atlassian Rovo), `/exit`. Then run the test script |
| "sandbox login expired" | The `sf` login to `yv-partial` expired | `sf org login web --alias yv-partial --instance-url https://test.salesforce.com` |
| "no current sprint Process" | No `Sprint N (DD/MM-DD/MM)` Process in YV20 covers today, or it has no tasks | Anna creates the Process and puts the tasks under it as Parent (section 3) |
| No Issue on Thursday | The Mac was off, or `gh` is logged out | Run `bash ~/yv-weekly/run.sh`; check `gh auth status` |
| "failed: <types>" in the log, or inventory types named in section 7 | Too many parallel `sf` calls, or a network drop | Run `bash scripts/weekly/pull-inventory.sh` again, then the test script |
| A build task's layouts at 0 while the page exists | The page is not a Lightning record page of that object, or it was built by someone outside the orders team, or the page retrieve failed (`_pages/_ERROR.txt`, section 7) | Read the object's section in `sources/local/org-snapshot-<date>/_pages.md`; name the object's API name in the Jira task or sprint tab row |
| A portal task scored lower than what you see in the site | The component is not in the 29 types, or its retrieve failed (section 7) | Read the evidence line; name the component in the Jira task description so the check finds it |
| Atlassian notice about v1/sse | Atlassian retires the old endpoint for `https://mcp.atlassian.com/v2/mcp` | Keep the "Atlassian Rovo" connector signed in; the job allows both |
| The report or the test names a refused tool call | The headless session has no one to approve it: a `cd`, loop, variable, redirect or a command not on `--allowedTools` | If the command is read-only and needed, add it to both scripts and to `scripts/weekly/headless-rules.md` through a PR; otherwise tighten the rule that let Claude try it |

## 6. Using Claude Cowork for this

Claude Cowork (the Cowork tab of the Claude desktop app) is for the planning and follow-up work around the sprint: reading the weekly report, updating the plan workbook, preparing meetings, drafting messages. Claude Code is still the tool for anything that changes this repo through git, and the scheduled check runs on its own.

**Set-up, once:** open Cowork, give it this repo folder (`yv-orders-master`) and, for the workbook, the SharePoint folder `06 תכנון וספרינטים`; make sure the Atlassian and Microsoft 365 connectors are on.

**Rules to give Cowork** (they are in `CLAUDE.md`, ask it to read that first): Yad Vashem only; never deploy; never change Jira except what Lior or Anna asks in the prompt; English in the repo, Hebrew RTL for Yad Vashem deliverables; no em-dashes; documents may be committed only if they hold no personal information (D-031): check every sheet, and never commit the YV fields workbook or any exported records.

**Prompts that work:**

1. *Update the sprint tab from the report.*
   "Read `CLAUDE.md` and `plan/OPERATING-GUIDE.md`. Take the latest GitHub Issue labelled `weekly-report` (or the newest file in `reports/weekly/`). Using its 'Sprint tab update' table, update the current sprint tab of the plan workbook in `06 תכנון וספרינטים`: status, percent done, hours left per Jira key. Save it as a new version of the workbook. Do not change Jira."

2. *Prepare the Thursday planning meeting.*
   "Read `plan/OPERATING-GUIDE.md`, `plan/TEAM.md`, `decisions/D-029-*.md` and the latest weekly report. Give me one page for the Thursday meeting with Anna: per person on track / at risk / blocked and why, what carries over to the next sprint, open questions that block work, and decisions we need. English, short."

3. *Draft the next sprint tab.*
   "Read `plan/OPERATING-GUIDE.md` section 4, `plan/SCHEDULE.md`, `plan/EPICS.md`, `tickets/Data Migration/` and the latest weekly report. Draft the next sprint tab in a new version of the plan workbook: a research task and a build-and-layouts task per entity with hours by the D-030 formula, assigned per `plan/TEAM.md`, carry-over first. Show me the draft before saving."

4. *Before Anna opens the sprint in Jira.*
   "Read the approved sprint tab and `plan/OPERATING-GUIDE.md` section 3. List, for Anna, every task to create in YV20: summary, assignee (Jira display name from `plan/TEAM.md`), original estimate. Do not create anything in Jira."

5. *Status of one person.*
   "From the latest weekly report and the tasks under the current sprint Process in YV20, what is the status of <name>: tasks, hours left, what is blocking them, what they owe. Read only."

6. *Commit the approved plan.*
   "Read `CLAUDE.md` and D-032. Copy the newest approved plan workbook from `06 תכנון וספרינטים` into `plan/workbooks/` (remove the previous version there), check every sheet for personal information (D-031), run `python3 scripts/plan_to_md.py \"plan/workbooks/<file>\"`, update the 'Current' version in `plan/OPERATING-GUIDE.md` section 1, and open a PR. Do not merge." (Needs git: run it in Claude Code, or have Cowork prepare the files and commit them with Claude Code.)
