# Object: Bundle Item

## Salesforce Object Details

| Property | Value |
|----------|--------|
| Object Label | Bundle Item |
| API Name | Bundle_Item__c |
| Status | Draft |

`Bundle_Item__c` already exists in `yv-partial` (custom object, label "Bundle Item", one record type "Master", checked read-only with `sf sobject describe`). The object name is therefore not an open question; its reuse is the proposal here.

Purpose, per the DD: the link object between the Bundle and the Product, a many-to-many relationship (a bundle holds several products, and the same product can appear in several bundles). Each record states one product in the bundle and its quantity, and it is the basis for breaking the bundle into order lines when the order is placed (Doc 1 04-entities.md, "פריט חבילה (Bundle Item, Custom)"; Doc 2 06-processes/01-products-bundles-templates.md, entities table and A01-02). The bundle items are the order and quote lines shown in the invoice (בחשבון); they are not the schedule lines (those come from the template linked to the activity day subject; Doc 2 comment c146). Per D-018 the legacy activity type (`new_tour_type`) is the Bundle, and the day subject is a separate object, so nothing about the day subject belongs on Bundle Item.

Legacy source: the YV fields workbook has no entity and no field rows for Bundle Item (the sheets "שדות" and "PICKLISTS" contain nothing for it). The only legacy material is four intersect tables between `new_tour_type` and `new_yv_product` in the sheet "שדות - רבים לרבים": `new_new_tour_type_new_yv_product_required`, `new_new_tour_type_new_yv_product_optional`, `new_new_tour_type_new_yv_product_no_cost` and `new_tour_type_yv_product_required_no_cost`. Each lists only the two GUID columns (`new_tour_typeid`, `new_yv_productid`); there are no other columns, no quantity and no Hebrew labels. Every other field below is therefore grounded in the DD, not in a legacy column.

### Proposed Lightning Page section grouping

Two new sections. No field on this object belongs in the standard "System Information" section except the system fields; Created By and Last Modified By stay there.

- **General Info**: Name, Bundle__c, Product__c, Quantity__c, Default_Order__c, Requirement_Type__c, Payment_Type__c, Active__c
- **Channels & Audience**: Audience_Category__c
- **System Information** (existing standard section, not new): Created By, Last Modified By only

This grouping is a proposal for review, not a decision; the DD does not specify a Lightning Page layout.

## Open Questions

Per-field questions for Lior live in the **Questions** column. Cross-field items:

1. **No legacy entity.** Bundle Item has no entity or field rows in the YV workbook; only four many-to-many tables. All fields except the two keys come from the DD. The DD names three fields ("מוצר, כמות, חובה או רשות", Doc 2 entities table); the paid or free distinction comes from the DD text and comments c140 and c144. Please confirm that this set (Bundle, Product, Quantity, requirement type, payment type) is complete.
2. **How the four legacy tables become rows.** One Bundle Item per Bundle plus Product pair, with `Requirement_Type__c` and `Payment_Type__c` taken from the table it appears in (see the two rows). The split into two fields gives the fourth table (`new_tour_type_yv_product_required_no_cost`, mandatory and free) a place: חובה plus ללא תשלום. What if the same Bundle plus Product pair appears in more than one table? Row counts are not available (the workbook holds no data rows for these tables).
3. **Requirement and payment versus channel.** Channel availability of a product stays on Product2 (`Display_Channels__c`), so no channel field is proposed here (removed per instruction). Legacy has no channel column, while Doc 1 comment c142 says the mandatory and optional sets can differ between Tahal and online. Is one record per Bundle, Product and channel the intended model, or one record with a requirement type and payment type per channel? If per record, a single channel Picklist would be added here. This changes the fields on this object.
4. **Bundle-to-order link and several bundles per order (see 02_Bundle.md Open Question 18).** The DD says a bundle breaks into order and quote lines on ordering (A01-02) and keeps no field recording which bundle a line came from. If the order or the activity day can hold several bundles, a junction object between the order and the Bundle is proposed in 02_Bundle.md; this affects where the breakdown starts but not the fields of Bundle Item itself. Open: should the order line (OpportunityLineItem) keep a reference to the Bundle Item it came from? That would be a field on the order line, not here.
5. **Relationship types.** The DD says many-to-many without naming the types. The org has Master-Detail to the Bundle and Lookup to Product2. Please confirm, including whether `Product__c` should be required and whether a Bundle plus Product pair must be unique (the DD is silent).
6. **Record types.** The org has one record type, "Master". The DD does not define record types for Bundle Item. Confirm none are needed (the A1 ticket asks for a page per approved record type).
7. **Item order.** Answered (Lior, 11.11.2026): keep `Default_Order__c` (Number, built by Tal on 09.11.2026), the order in which the portal lays out a class's programme from the bundle items. The DD names no sequence field; the field is kept because the portal needs it. Implementation plan O9 is updated to match.
8. **Existing fields without a DD or legacy source:** `Active__c` and `Audience_Category__c` (see their rows). For `Audience_Category__c`, the level of the audience decision (Bundle, Product or Bundle Item) is a question for Lior; recommendation is to remove it from Bundle Item.
9. **Legacy ID.** The intersect tables have no key of their own, so no `Legacy_System_Id__c` is proposed here (unlike Product2 and Bundle). Should a composite external ID (Bundle GUID plus Product GUID) be created for reloads? Not stated in the DD, so none is proposed and Unique is blank everywhere.
10. **Terminology.** Hebrew labels use the DD wording ("חבילה", "מוצר", "פריט חבילה"), consistent with Open Question 19 of 02_Bundle.md. No legacy Hebrew labels exist for these tables.
11. **Lengths and types.** Quantity precision (4,0) is the existing org setting; the DD gives no precision.
