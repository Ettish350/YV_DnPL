# Weekly progress check (D-028, D-029, D-030)

Every Thursday 07:30 on Lior's Mac, before the planning meeting, so Lior and Anna plan from fresh numbers.

## What is measured
- **Jira (YV20)**: only the tasks whose Parent is the current sprint Process (`Sprint N (DD/MM-DD/MM)`; YV20 has no Jira sprints), their status, estimate and assignee.
- **Sandbox**: a fresh read-only metadata pull from `yv-partial` (`sf org list metadata`), compared with the previous pull. Build-and-layouts tasks are measured against the custom fields of the entity's approved object file in `tickets/Data Migration/` (except `Not built` rows) and against the record page of the target object, together.
- **Layouts** (changed 19.10.2026): `record-pages.py` retrieves read-only every FlexiPage and Layout that no managed package owns, and the `Orders` app, and writes `_pages.md` per object (record pages with label, D-030 name, Orders app assignment, who and when, fields placed; page layouts, edited or not). Per object, whatever the page's date: a Lightning record page assigned in the Orders app = 100; a record page built by an orders implementer and not yet assigned in the Orders app, or a page layout a person edited with no record page = 50 (Lior, 19.10.2026); nothing, or only the default layout Salesforce creates with the object = 0. A page without the Orders app assignment or the D-030 name `Order-<Object Name>- Record Page` is also listed as a mismatch (assign or rename). With an approved object file, approved fields not placed on the page are named in the evidence. Several objects in one task: the average.
- **Portal and other tasks** (no object file; changed 19.10.2026): every component that matches the task counts whatever its date, including work built before the sprint started. When the evidence includes an LWC, Aura bundle, Experience site bundle, navigation menu, labels or translations, the check retrieves them read-only (`sf project retrieve start --target-metadata-dir` into `sources/local/org-snapshot-<date>/_retrieve/<task key>/`) and reads the code against the task: does what the task asks = 100; screen built on mock data (`TODO-APEX`, mock arrays, no Apex or `@wire`) = 50, "UI built, data not connected"; partial = 50; nothing = 0. Until Issue #15 defines done per portal task, these rules are the definition.
- **Research**: the entity's object file in `tickets/Data Migration/`, on `origin/main`, in an open PR, or on any pushed branch without a PR. `research-progress.py` counts, per file and branch, the legacy fields the file has gone through (mapped by Old API Name, or listed under Dropped legacy fields) out of all fields of the legacy entity in `sources/שדות מערכת ישנה.xlsx`, and writes `sources/local/org-snapshot-<date>/_research.md`. Percent done (D-030 as amended 19.10.2026): `Draft` 60 x the share gone through (40 when the object has no legacy entity), `In review` 70, `Approved` 100. The report gives fields gone through, the last push and the fields still left. Work only on a laptop cannot be seen, so implementers push their branch at the end of every work session.
- **Git work**: commits on `main`, PRs opened, merged and open, Issues opened, per person, over the last 7 days.
- **Open questions**: `question` Issues, who raised them and who owes the answer.

The sandbox pull (`pull-inventory.sh`, about 45 seconds), the field count (`research-progress.py`, a few seconds) and the page retrieve (`record-pages.py`, about 45 seconds) run before Claude starts, because the headless session cannot run shell loops. It lists 29 metadata types: the 18 of the first version, plus where portal work lives (Profile, CustomLabel, Translations, StaticResource, NavigationMenu, DigitalExperienceBundle, DigitalExperienceConfig, AuraDefinitionBundle, ApexPage, SharingSet, PermissionSetGroup; added 19.10.2026). At most 6 calls run at once (29 at once fail with "fetch failed"); a failed type is retried once, never overwrites a good file, and is named in `_inventory/_FAILED.txt` and in the report.

**Scoring** (22.10.2026): `score-tasks.py` scores every task, for the weekly check and the daily status alike, so the two emails always agree. Claude reads Jira and writes `jira-<date>.json`, judges the portal and other tasks (the only judged scores) into `judgments-<date>.json`, then runs the script, which scores research, build and layouts by the rules above and writes `tasks-<date>.json` (each row with the `rule` that produced it), `scores-<date>.json` (working days left, status per person, Score disputed) and section 9 of the report. A judged score that differs from the previous run while none of its listed components was created or modified since the previous snapshot is not taken: the previous score stays and the task is listed under Score disputed for Lior. Status per person: blocked if an open task's evidence says blocked, else at risk if hours left > working days left x 6, else on track.

People are joined across Jira, git and GitHub through `plan/TEAM.md`. The report has one section per person (on track, at risk or blocked) and a sprint tab table that Lior's Claude uses to update the plan workbook. Full steps: `.claude/commands/weekly-progress.md`.

## What it changes in Jira
Only tasks under the current sprint Process in YV20 (created from 12.10.2026); never the older YV20 tasks or Process items, never the Process itself, and nothing at all when there is no current sprint Process. For those tasks: one comment per task per run with the evidence, and a forward-only status move when the evidence is clear (To Do to In Progress; at 100%, research to Done, everything else to Ready for testing sandbox). Never backwards, never other fields or tasks (D-028). The test script changes nothing in Jira and lists what it would change.

## How the report arrives
It is written to `reports/weekly/progress-<date>.md` in the clone and posted as a GitHub Issue labelled `weekly-report`, titled `Weekly progress <date>: X% done, Y hours left`. Lior and Anna watch the repo, so GitHub emails it to them. GitHub does not email Lior about an Issue his own account posts, so after the Claude session `run-weekly-progress.sh` builds an email with the daily email's template (`scripts/daily/build-daily-email.py --weekly`: a link to the Issue, the headline bar, team table, since last check, per-person tables, then Score disputed, reviews he owes, Jira changes by the run and findings, the last three from `extras-<date>.json` that Claude writes in step 7) and sends it to `LiorP@malamteam.com` with the same exact-content send call as the daily, retried once. Subject: `YV sprint weekly DD.MM: X% done, Y h left, N days left`. Working files: `sources/local/weekly/`.

- Needs on the Mac: `claude` logged in, `sf` with the `yv-partial` login, the Atlassian connector in Claude Code (authenticated), and `gh` logged in.
- **Shell rules** (`headless-rules.md`, added 19.10.2026). Both scripts pass it with `--append-system-prompt-file`. The headless session has no one to approve a call, so anything outside `--allowedTools` is refused. Claude Code refuses a git command after any `cd` (even into the same folder), a `for` loop or a `$variable`, a redirect, and a pipe into a command that is not allowed. The 19.10 test runs lost `git show` calls this way, not because of the quotes or the space in `tickets/Data Migration`. The rules say: no `cd`, one simple command per call, pipes only into read-only filters (`grep`, `head`, `tail`, `wc`, `sort`, `uniq`, `cut`, `tr`, `jq`, which are on the allowlist with `git ls-tree`), no redirects, no scripts, files written only inside the repo with relative paths. `Edit` works inside the repo through `--permission-mode acceptEdits`. `Write` has to stay on `--allowedTools` unscoped: without it, or as `Edit(<folder>/**)`, the headless test session refused every Write, even inside the repo (probed 19.10.2026 from a worktree). Keep the allowlists of `run-weekly-progress.sh` and `test-weekly-progress.sh` the same, apart from posting (Issue, label, email).
- `--allowedTools` in `run-weekly-progress.sh` names the connector as `mcp__atlassian`, `mcp__claude_ai_Atlassian` and `mcp__claude_ai_Atlassian_Rovo` (the claude.ai Atlassian connectors; the Jira site is malamteam.atlassian.net). The plain `Atlassian` connector uses Atlassian's v1/sse endpoint, which Atlassian is retiring in favour of `https://mcp.atlassian.com/v2/mcp`; when it stops, keep `Atlassian Rovo` signed in (`claude`, then `/mcp`). If `claude mcp list` shows another name, change it in `run-weekly-progress.sh` through a PR.
